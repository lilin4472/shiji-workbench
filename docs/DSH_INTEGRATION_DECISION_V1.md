# 识机 V1：DeepSeek Harness 使用与替换决策

## 结论

识机不自己重写完整通用 Agent 内核，也不把 DeepSeek Harness（DSH）当成不可替换的产品核心。

采用“两层方案”：开发期用 DSH 做插件能力验证；产品期由识机自己的最小任务编排器承载稳定业务流程，DSH 仅保留为可选后端。

开发期/可选后端采用“DSH 本地运行时 + 识机自有控制层”的混合方案：

- DSH 负责模型会话、工具调用循环和经过审查的通用插件。
- 识机负责业务任务、对象 Schema、搜索/抓取路由、预算、超时、取消、结果校验、本地存储和密钥生命周期。
- 前端只调用识机的 `AgentRunner` 契约，不得导入 DSH 的内部包、事件类型或配置文件。
- DSH 以独立子进程运行；版本、插件、Node 运行时一起锁定，升级只能通过兼容性门禁。

当前实现边界必须明确：识机启动的是官方 DSH SDK runtime，确实会进行真实模型会话；但 V1 使用的是“model-only”配置，显式关闭 DSH skills、Bash、Jobs、workspace context 和通用工具。自动识别模式下，原始自由输入先进入 DSH 意图会话，再开始豆包搜索；识机只负责 schema 校验、金额/时间证据门禁、证据绑定和候选保留，不再用关键词正则替代用户意图。因此“中文数字没有被解析”首先是旧入口没有把原文交给 DSH，不是 DSH 模型不会中文；在意图会话之前被本地门禁拦截的请求，根本没有发生 DSH 模型调用。

产品自己的编排器只做识机需要的有限流程（搜索、抓取、核验、结构化报告和重试），不承担通用编码代理的全部能力。这样 V1 不依赖 DSH 预览版的安装和升级，但仍能用 DSH 快速测插件；若 DSH 后续稳定，可继续作为一个后端接入。

## 已确认事实

1. 当前项目的 Electron 已启用 `contextIsolation`、关闭 `nodeIntegration`，适合把运行时和密钥控制放在主进程。
2. 官方 DSH 仍是开发预览，官方文档明确提示接口可能发生破坏性变更。
3. 官方 Web 能力通过稳定的 `ctx.web` seam 分离搜索和抓取；模型看到的 `web_search`/`web_fetch` Schema 不需要随供应商变化。
4. 本机全局 `dsh` 是 `0.1.0-rc.6`；本次尝试直接运行 `@deepseek-ai/dsh@0.1.1-rc.2` 返回 npm `ETARGET`。该版本源码标签存在，但不能假定有可直接安装的同版本 npm 包。
5. `0.1.1-rc.2` 源码检出约 7,903 个文件、48.7 MB（未含依赖和构建产物），完整 Web UI 与标准编码代理不适合原样随识机分发。
6. DSH 自带凭据文件是可读明文配置，不应作为识机的“本机加密保存”实现。Key 应由 Electron 主进程使用 Windows 加密能力保存，运行时只通过受控环境传入。
7. `0.1.1-rc.2` 源码内已经提供官方 TypeScript SDK Client：它负责启动 SDK runtime、stdio JSON-RPC、请求超时和 EOF → SIGTERM → SIGKILL 关闭流程。识机不重复实现这套协议和进程回收，只在它前面维护版本门禁、环境隔离、身份校验和错误转换。
8. 官方 Python SDK 单文件 runtime 的构建脚本当前只列出 Linux/macOS，明确把 Windows 作为非目标；Windows V1 不能直接使用官方单文件发布链。
9. 本机全局 `dsh 0.1.0-rc.6` 没有名为 `sdk` 的 profile；它只是开发环境中的旧版 launcher，不能作为识机运行时来源。
10. `0.1.1-rc.2` 在 Windows + Node `24.19.0` 下可完成完整 Host TypeScript 编译及 Host 构建，但官方 SDK runtime 构建脚本在 Windows 直接启动 `pnpm.cmd` 时触发 `spawn EINVAL`；这属于官方 Windows 构建链缺口，不是识机业务代码问题。
11. 依照官方部署逻辑补齐 16 个 legacy-hoist 依赖并实体化 2 个符号链接后，SDK runtime 能在完全不提供 Key 的情况下完成 `initialize`，返回 `deepseek-harness-sdk-runtime@0.0.1` 并正常关闭。
12. 该默认闭包约 146.0 MiB、22,764 个文件。连续三次 Node 24 冷启动为 365–387 ms；连续三次复用 Electron 44 自带 Node 为 382–407 ms。复用 Electron 可避免再附带第二套 Node，但该握手测试不代表搜索、工具调用和原生模块路径已经通过完整验收。
13. DSH 源码包版本与 SDK runtime 协议身份版本不是同一个概念：本轮源码锁为 `0.1.1-rc.2`，实际握手身份为 `deepseek-harness-sdk-runtime@0.0.1`。控制器必须分别校验，不能继续用源码版本冒充协议版本。

## 三种方案评估

| 方案 | 短期速度 | 后期维护 | 主要风险 | 决策 |
| --- | --- | --- | --- | --- |
| 直接绑定完整 DSH/Web UI | 快 | 高成本 | 预览版变更、包过重、权限面过大、前端被内部 API 绑死 | 不采用 |
| 完全自研通用 Agent 内核 | 慢 | 自己掌控但工作量大 | 工具循环、会话、重试、流式事件、取消、权限和边界调试全部重做 | 不采用 |
| 识机最小任务编排器 | 中等 | 最可控 | 需要实现有限的任务状态机、工具端口和结果校验 | 产品 V1 采用 |
| 自有控制层 + DSH 子进程适配 | 中等 | 可控但受预览版影响 | 需维护适配器、运行时打包和版本验收 | 开发期/可选后端采用 |

这里的“最小任务编排器”也不是再造一个通用 Agent；它只按识机固定任务图执行，并把模型调用当成一个可替换步骤。它应保持薄，只解决识机特有的稳定性和数据契约。

## 识机自有边界

`AgentRunner` 在主进程控制所有运行时，DSH 适配器的职责固定为：

- 启动和关闭锁定版本的 DSH 子进程；
- 为一次任务建立独立 session，设置总超时和最大搜索/抓取预算；
- 将 DSH 通知转换成识机自己的 `HarnessRunEvent`；
- 对最终结果做 JSON Schema 校验，失败时只允许一次受限修复，不把自由文本当业务数据；
- 任务取消时终止子进程并清理进程树，避免无止境挂起；
- 记录脱敏后的本地任务日志，不记录 Key；
- 向 DSH 传入临时环境变量，不写入 DSH `.credentials.yaml`；
- 将搜索和抓取抽象成识机自己的端口，未来可替换 DeepSeek、Firecrawl、Jina 或中文搜索供应商。

其中进程与协议分工进一步冻结为：

- `DshRuntimeController`：验证锁定的 DSH/Node 精确版本，清除继承环境中的凭据，拒绝不兼容版本，验证 SDK peer 身份，把底层异常转换为识机可控错误。
- 官方 `HarnessClient`：真正拥有 DSH 子进程、stdio JSON-RPC 和关闭升级流程。
- `DshAgentBackend`（后续实现）：把官方 SDK 的通知与结果转换成识机 `AgentRunner` 契约；它是唯一允许理解 DSH 事件的业务适配层。

`DshRuntimeController` 不自行实现 JSON-RPC，不把 DSH profile、Cordis 配置或事件类型暴露给前端，也不从凭据文件读取 Key。

前端只能看到：状态、进度、结构化结果、证据引用和可解释错误。前端不负责启动 DSH，也不直接读取 Key。

附近个人/企业、集团组织、产业关系和获客属于识机产品自己的 Task/SearchPlan 与数据契约，不做成 DSH 私有插件数据。DSH 可以在已筛选材料上归纳个人经营参考或关系说明，但不能决定搜索路线、计算地理距离、凭空创建集团隶属关系，也不能让获客模块另起一套与产业链脱节的数据。

## 开发期 DSH 验证组合

第一轮只验证最小组合，不安装插件大杂烩。验证结果只决定产品后端选择，不自动进入安装包：

1. 模型：用户自己的 DeepSeek Key，固定使用当前 `deepseek-v4-flash` 做低成本默认；非复杂任务关闭默认高思考，复杂分析由产品显式开启。
2. 搜索：第一候选为 DSH 内置 DeepSeek search，同一把模型 Key 可完成 POC；开发探针直接调用搜索 Provider，避免通用 Agent 工具循环额外产生前后模型调用。单次最多 1 次原生搜索、最多 5 条来源。
3. 抓取：先测内置静态 HTTP fetch；它不负责 JS 页面、反爬、PDF 和复杂附件。
4. 结构化输出：识机薄插件/适配器提供业务结果 Schema，至少覆盖 `Opportunity`、`Company`、`Evidence`、`AnalysisResult`、`Recommendation` 和 `ActionItem`。
5. 暂不启用 Perplexity；它增加第二个付费 Key 和一层生成式答案，不适合作为第一证据源。
6. Firecrawl 只作为困难网页、JS、反爬和 PDF 的候选后端，须先确认与锁定 DSH 版本兼容；不能默认把它变成所有请求的必经成本。

首轮实测裁决：DeepSeek Search 已能返回中文政府招标源，可作为招标发现的默认候选，但尚不能单独承担地域精确过滤、工商信用核验和网页正文清洗。识机必须继续做来源分级、域名规则、重复去除和抓取失败标记。

工商信用对照补充：两个公开企业主体的“完整名称 + 经营异常/严重违法/行政处罚/失信被执行人 + 官方”单次搜索均返回 0 条来源；官方域名搜索也没有精确命中。该结果只证明当前发现链没有拿到证据，不证明企业没有风险。工商信用不得沿用通用搜索的“搜不到即为空”语义，必须采用三态证据模型（已核验、未核验、发现记录），并保留官方页面人工核验或本地材料导入通道。DeepSeek Search 因此不晋级为工商信用唯一后端。

实现边界补充：工商信用发现服务只依赖识机自己的搜索来源结构和一个可替换搜索函数，DSH/DeepSeek 不进入报告数据契约。AnySearch 与 Tavily 复用同一固定测试集、搜索端口和三态报告；用户选择本机全局默认，也可在单次任务覆盖。系统不得为某个供应商复制业务逻辑，不自动双搜或静默回退，也不宣称任一供应商普遍更准确。

官方材料补充路径：当官方站点拒绝自动抓取时，用户可自行下载或截图后导入本地证据仓。导入阶段只做文件校验、复制、SHA-256 去重和元数据记录，不调用 DSH，也不向模型上传；后续解析器必须通过识机自有端口接入，并在解析结果经用户或规则确认前保持“未核验”。

## 为什么不能只用 DSH 内置 HTTP

招标附件、PDF、JS 渲染页、验证码/反爬和工商公开页是识机的高风险场景。DSH 内置 HTTP 不能宣称已经解决“招标详情”和“工商信用”，也不进入正式机会任务。识机自有读取层负责静态 HTML、文本和文字 PDF，允许公开商业转载，但每次连接固定到已校验的公网地址并限制跳转、时长和体积；JS 页面、验证码、复杂反爬和扫描件继续明确失败或等待 OCR。

证据策略应是：官方来源优先，抓取失败明确标记，允许用户把 PDF/截图/网页文件导入本地核验；“未找到”不得输出成“没有风险”。

## DSH 可选后端升级门禁

任何 DSH 或插件升级必须同时通过：

- 进程启动与版本识别；
- 无 Key 启动错误可控且不泄露凭据；
- 单轮文本任务、超时、取消、重启；
- `web_search` 和 `web_fetch` 的事件/错误映射；
- 结构化结果 Schema 校验；
- 5 类固定回归任务：招标发现、招标详情、政策链、工商公开风险、个人附近机会；
- Windows 安装包启动和卸载后的本地数据保留；
- 旧任务记录仍能读取。

任何一项失败，保留上一版可选后端，不随软件自动升级。运行时与插件必须可回滚；产品自己的最小编排器不随 DSH 版本变化。

## Windows 发布裁决

- DSH 内核与官方 TypeScript SDK Client 可以在 Windows 运行，不能把“官方单文件脚本不支持 Windows”误判成“内核不能用”。
- 官方 `0.1.1-rc.2` Windows 部署链不能原样进入生产：需要识机维护一个很薄、可回归的依赖补齐和链接实体化步骤。
- 能力包启用前必须同时匹配：DSH 源码版本、Electron/Node 版本、SDK runtime 身份、必需入口、文件总数及完整目录树 SHA-256。目录摘要必须同时存在于能力包清单和识机自身的可信发布锁；只信任能力包自报哈希不能防止清单与文件一起被替换。
- 默认 146 MiB 闭包不随 V1 主程序强制安装。它作为可下载、可删除、版本锁定的“DSH 能力包”保留；主程序缺少能力包时仍由识机最小编排器工作。
- 能力包优先复用 Electron 的 Node 模式，不再携带额外 Node。只有完整跑通模型、搜索、抓取、取消、原生模块及安装/卸载回归后，才可从开发能力包晋级为用户可选能力包。
- 不修改 DSH 核心源码。Windows 构建兼容和产品事件转换全部留在识机边界层，便于未来替换或升级。

## 本轮不做

- 不把 DSH Web UI 打包进识机。
- 不接用户 Key 到聊天、代码、日志或服务器。
- 不在没有固定测试集的情况下宣称某个搜索插件“最好”。
- 不同时启用多个同类搜索提供商让模型自由选择；这会导致重复花费、结果不可复现和 provider ambiguity。
- 不为兼容预览版而修改 DSH 核心；必要改动放在识机适配器或独立插件。

## 下一步实现顺序

1. 先定义识机自己的 `AgentRunner`、搜索/抓取端口、结果 Schema 和假运行时测试，不需要真实 Key。
2. 实现 `DshAgentBackend`，把官方 SDK 通知映射为识机事件；它只能依赖 `DshRuntimeController`，前端不得感知 DSH 类型。
3. 把已经验证的 Windows Node carrier 构建步骤固化为独立能力包流水线，锁定 `0.1.1-rc.2`、Electron/Node 版本和插件清单；能力包仍不进入默认安装包。
4. 在设置页加入本地 Key 输入、测试连接、删除 Key；Key 只进主进程。
5. 用户在本机设置页输入 Key 后，先跑 DSH 与自有编排器的 5 类回归任务和成本记录。
6. 用真实 Key 跑完模型、搜索、抓取、取消、原生模块和安装/卸载回归后，再决定是否向用户开放 DSH 能力包；Firecrawl/Jina/中文搜索后端都通过识机自己的搜索/抓取端口接入。
